# P15 D1 — environments

Generated by `tools/p15-env-diff.py` from `config/environments.json` (the file the deploy reads), so
this page cannot describe a configuration nobody deploys. Every difference between two environments
carries a reason: the tool refuses to pass while any difference is unexplained.

| Environment | Purpose | Data | Cost |
|---|---|---|---|
| `local` | development: docker compose up, fixtures, no network to the venue | mock + fixtures (seeded by `make seed`) | $0 |
| `preview` | one per pull request, ephemeral: does the branch boot and answer? | mock; a branch database seeded with fixtures, dropped with the environment | ~$0 (branch compute only) |
| `staging` | pre-prod rehearsal: the whole order path, with fake money and a real book | real Polymarket market data and tape; no real order leaves the building | ~$10/mo (one small host; a branch database) |
| `canary` | our own money, real orders, internal accounts only: the $50 of the P14 D7 checklist | real | shared with prod |
| `prod` | live: other people's money | real | ~$72/mo at launch (see docs/P15-deployment.md D2) |

## What each difference is for

* **local vs preview — `PGM_AUTH_MODE`**: `dev-header` vs `bearer`  
  local only. A dev identity on any environment with a public URL is an authentication hole with a friendly name.
* **local vs preview — `PGM_DB_PATH`**: `var/polygm.db` vs `(empty)`  
  it is the local database's location, and nothing else.
* **local vs preview — `PGM_LOG_FORMAT`**: `text` vs `json`  
  local is text because a human is reading it; every deployed environment emits JSON, and the CI log-redaction check runs against the JSON shape.
* **local vs preview — `PGM_REQUIRE_SECURITY_ENV`**: `(empty)` vs `1`  
  local is unset so a developer can boot from .env without the full security plane; preview, staging, the canary and prod all set it, because P14's F9 was the deployed API running the development identity shape in production.
* **local vs preview — `POLYGM_ENGINE`**: `sqlite` vs `postgres`  
  local runs SQLite because a laptop has no Postgres and the seed is instant; every deployed environment runs the engine that will hold real money. Preview runs Postgres specifically so a migration that only works on SQLite cannot pass review.
* **local vs staging — `PGM_AUTH_MODE`**: `dev-header` vs `bearer`

## The invariants, checked on every run

| Environment | Knob | Must be | Why |
|---|---|---|---|
| `prod` | `PGM_REQUIRE_SECURITY_ENV` | `1` | the deployed box runs the production identity shape: no dev header, and a missing KEK is a boot failure (F9) |
| `prod` | `PGM_AUTH_MODE` | `bearer` | the only way in is a session token |
| `prod` | `POLYGM_TRANSPORT` | `live` | prod is the venue |
| `prod` | `POLYGM_ENGINE` | `postgres` | SQLite is dev/CI only and must never hold real money |
| `prod` | `PGM_LOG_FORMAT` | `json` | the log scanner and the redactor read JSON lines |
| `staging` | `POLYGM_TRANSPORT` | `mock` | staging must be able to exercise the whole order path without a real order ever leaving the building |
| `staging` | `PGM_REQUIRE_SECURITY_ENV` | `1` | staging is prod-shaped for auth: a staging-only identity convenience is how F9 happens twice |
| `canary` | `POLYGM_TRANSPORT` | `live` | the canary exists to place real orders, with real money |
| `canary` | `PGM_REQUIRE_SECURITY_ENV` | `1` | real money, production shape |
| `local` | `PGM_AUTH_MODE` | `dev-header` | the dev header is the laptop's convenience, and only the laptop's |
| `local` | `PGM_REQUIRE_SECURITY_ENV` | `(empty)` | unset locally: the developer's KEK comes from .env or the fixtures |
| `preview` | `POLYGM_TRANSPORT` | `mock` | a per-PR environment must never reach the venue |
| `preview` | `POLYGM_ENGINE` | `postgres` | preview runs the real schema against a branch database, not SQLite |
