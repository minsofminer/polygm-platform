## 1. The one thing that is actually broken

Both themes' reds clear 4.5:1 on the page background and **miss it on `bg.elevated`**, which is where data
panels live and where a loss number is rendered smallest:

| theme | token | hex | on `bg.base` | on `bg.elevated` | verdict as text |
|---|---|---|---|---|---|
| light | `action.sell` / `result.loss` | `#dc2626` | 4.83:1 | **4.43:1** | fails AA (4.5:1) |
| light | `action.buy` / `result.profit` | `#15803d` | 5.02:1 | 4.60:1 | passes |
| dark | `action.sell` / `result.loss` | `#ef4444` | 5.13:1 | **4.38:1** | fails AA |
| dark | `action.buy` / `result.profit` | `#16a34a` | 5.86:1 | 5.00:1 | passes |

This does **not** currently mis-render anything, because D4b already decided the PnL *number* is always
`text.primary` and colour is reinforcement on chips/carets/depth bars (all non-text, where 3:1 is the bar and
both hues pass). It becomes load-bearing the moment anyone paints a number or a small label in the money hue.

## 2. Two ways out, pick one

**A. Deepen the reds (one-line change each theme, same family).**
Light `#b91c1c` → 6.47:1 / 5.93:1, i.e. AA text everywhere, still recognisably the current red. Note its
distance to `outcome.no` (`#D55E00`) rises only to 9.9 ΔE, so the `never-same-row` layout rule stays
necessary either way. For dark, `#ef4444` has no same-family deepening that clears 4.5:1 on `bg.elevated`
(every darker red I measured falls under the 3:1 UI bar on the dark panel), so dark either keeps colour as
non-text (already true) or takes a lighter red such as `#f87171`-adjacent — which the script can re-grade on
request.

**B. Keep the palette and make the non-text boundary explicit.**
Money hues stay exactly as locked; `web/DESIGN.md` gains one line: *`action.*`/`result.*` may fill or stroke,
never set text — text in a money hue must use `*-text` tokens.* Zero brand change, and it matches what the
design system already does. The `pnl-never-coloured-text` rule plus G6.6 of the gate already enforce the
number case; this closes the small-label case.

I recommend **A at the next scheduled brand revision**, and treat B as done. A is a two-value palette change
(`light.action.sell` → `#b91c1c`, clearing 6.47:1 / 5.93:1) and would restore the option of a coloured small
label; it touches a `fixed` field, so it waits for you. If you prefer A, the sequence the tooling enforces is
in the script's footer, and `tools/repin-p02-digest.py --apply --ack=color` refuses to re-pin the certified
palette until `colour-audit` and both phase gates pass — so an approved recolour cannot quietly go unaudited.
